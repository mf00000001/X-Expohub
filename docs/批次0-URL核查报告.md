# 批次 0 结果：100 个展会官网核查

> 执行时间：2026-11-03 ｜ 脚本：`expohub-backend/scripts/persona/check_urls.py` / `merge_urls.py` / `finalize_urls.py`
> 数据：`data/expo_candidates_final.json`、`data/batch0/url_check.json`、`data/batch0/summary.json`

## 1. 结论

**100 个条目，去重后 94 个唯一展会。规模前提成立，但有一处规则必须先改。**

| 状态 | 条数 | 含义 | 采集方式 |
|---|---|---|---|
| `crawlable` | **49** | 能打开 + 确认是这家展 + robots 允许 | 纯 HTTP 直接采 |
| `crawlable_if_std` | **27** | 同上，但站点**没有 robots.txt** | 纯 HTTP，需先改 robots 规则 |
| `needs_render` | **8** | 域名对，正文抓不到（前端渲染） | 需 headless |
| `blocked_by_site` | 4 | 403 / TLS 握手拒绝 | 人工录入 |
| `dead` | 3 | 连接被重置、站点不可达 | 人工录入 |
| `suspicious` | 2 | 能打开但内容不是这家展 | 换 URL 或剔除 |
| `duplicate` | 6 | 与另一条是同一展会 | 统计时剔除 |
| `no_url` | 1 | 亚洲户外展已停办 | 替换 |

对照原计划「约 70~80 个可自动抓、20~30 个需人工」：**实际纯 HTTP 可采 76 个，需人工 10 个**。预估基本准确，甚至略乐观。

## 2. 怎么查的：三轮，每轮都在推翻上一轮

**第一轮（凭档案和记忆填 41 个 URL）**：只有 28 个可访问且对得上，命中率 68%。抽样验证时更差——AWE 和光亚展两个我"很确定"的域名全错。

**第二轮（5 个子代理并行搜索查证 72 个缺口）**：把命中率拉到 80%，同时暴露出数据集本身就有错：
- `SIMM` 已改名 `ITES`，旧域名只剩 2004 年内容
- 智博会 → **世界智能产业博览会**，物联网博览会 → **世界物联网博览会**
- 宁波消博会 2019 年并入**中国—中东欧国家博览会**，原独立站停在 2019
- 中国国际家具展正确域名是 `.cn`，不是 `.com.cn`
- 亚洲户外展 2019 年后停办，南京现为 ISPO 体系

**第三轮（修核查方法本身）**：第一、二轮的数字有一批假阴性，是我脚本的 bug：

| bug | 后果 | 修法 |
|---|---|---|
| 不处理 gzip | 读到压缩字节，标题为空 → 判成"不是这家展" | 显式 `Accept-Encoding` 并解压 |
| 按"解出汉字最多"选编码 | UTF-8 字节被 GBK 解成 `涓栫晫...` 乱码 | 利用 UTF-8 自校验：严格解码成功就用它 |
| SSL 证书失败即判死 | 6 个缺中间证书的站被当成"打不开" | 核查阶段降级重试，只读公开页 |
| 只按关键词判 | 英文站（`CEE - China Education Expo`）和 JS 站全被判存疑 | 加"域名是否跳转"作为独立判据 |

一个数字的演进能说明方法比数据更重要：同一批 URL，**28 → 62 → 91**。三次都不是换了数据，是换了判断方法。

## 3. 五个关键发现

### 3.1 URL 不能靠猜，这一步必须当成一次采集

我最初以为"100 个展会"的瓶颈是能不能抓到内容。实际瓶颈在前面：**得有 URL**。

凭记忆和现有档案填的 41 个里，错的方式有三种：域名版本错（`.com` vs `.cn`）、改版后子域变了（`hktdc.com/hklightingfairae/en` → `hklightingfairae.hktdc.com`）、旧站没下线但已停更（点进去是 2019 年的页面）。

**这意味着"展会官网发现"是画像管线的第 0 个采集任务，不能假设它是现成的输入。** 好消息是它可自动化：搜索 + 域名跳转检查 + 关键词比对，本次 99 个用了约 15 分钟。

### 3.2 robots 规则正在砍掉 40% 的可用数据源

27 条卡在"站点没有 robots.txt"。查了明细：**30 个 missing 里全是 404，没有一个返回 `Disallow: /`**。

现有 `expo_scraper.py` 的写法是：

```python
except Exception:
    rp = None      # 取不到 robots.txt 就判不允许
return False
```

这与 RFC 9309 相反——标准规定 **4xx 表示"没有任何限制"**。现状等于：因为对方没写"禁止"，所以我们认定它"禁止"。

按现规则可用 49 条（52%），按标准 76 条（81%）。**这一条规则决定了近三成的数据量**，是本轮最该先定的事。

真正的合规风险不在 robots 文件有无，而在于是否只抓公开页、是否遵守明确禁止、是否控制频率、是否丢弃个人信息。现有 scraper 后三条都做到了。

### 3.3 越是头部大展，越抓不动

8 个需要渲染的全是重量级：进博会（`ciie.org`）、工博会（`ciif-expo.com`）、世界智能产业博览会、ITMA 纺机展、中国物流与供应链博览会。

它们的标题是空的、正文由 JS 生成。**纯 `requests` 在这类站上拿不到任何字段**，必须上 headless 浏览器，成本高一个量级。

这条会直接影响技术选型：如果 E1（观众数/展商数）恰好压在头部展上，就得先决定"值不值得为 8 个站引入浏览器渲染"。

### 3.4 "凑够 100 个"会必然撞车

边界加压 20 个里，6 个和主干组是同一展会：CMEF、CCMT、ITMA、CIHS、广交会、SIAL、深圳礼品展、百货会。

原因很直接：中国真正有规模的 B2B 头部展就那些，按"18 品类 × 4 档"切分时，**"边界模糊"档只能从相邻品类里找，而相邻品类的头部展已经在主干里了**。

去重后 94 个。这个数不该硬凑回 100——按原定"去重后 92~100，不为凑整硬塞"，应该接受 94，把空出的额度补到真正薄弱的品类上：

| 品类 | 可用/总数 | 问题 |
|---|---|---|
| 办公箱包及休闲用品 | 2/6 | 最弱，露营/户外/箱包三条线都没找到稳定官网 |
| 鞋类 | 2/4 | 两个能否访问都是 403 |
| 家居装饰品 | 3/5 | 上海家居装饰那条已确认不存在独立展 |

### 3.5 有 2 个 URL 打开了但内容不是这家展

- `b-camping` → `hweexpo.cn` 实际是 **SVE 上海国际休闲运动车展**
- `furniture-china` → `furniture-china.cn` 现在跳转到 **jiagle.com（华夏家博会，B2C 消费展）**

这两个正是原方案里担心的情形：域名还在、能打开、看着像，但内容已经换了。**只判 HTTP 200 会把它们当成功**——这也说明"域名是否跳转"这个判据必须保留。

## 4. 对下一步的影响

1. **批次 1 可以开始**，但先解决 robots 规则。若按标准口径，可采样本 76 个，够算品类内分位；若维持现规则只有 49 个，18 个品类分下来每类不到 3 个，**分位数没有统计意义**。
2. **headless 这 8 个先不做**。它们对应的字段（观众数、展商数）先走人工录入，等验证过 E1 真有用再补。
3. **人工通道必须现在建**。10~14 个站（403/渲染/停办）绕不过去，这是 CSV 导入器的直接需求。
4. **品类结构要修**：办公休闲、鞋类、家居装饰三个品类补不上，会让"品类内分位"在这三块失效，E2 的竞品数阈值也就无处校准。

## 5. 需要你定的三件事

1. **robots 规则改不改？** 建议改为"404/取不到 = 允许，401/403 或明确 `Disallow` = 禁止"。不改，样本量砍半。
2. **94 个就够，还是补到 100？** 我倾向 94 —— 缺口补在薄弱品类上比补数字有用，但那三个品类的官网确实难找。
3. **8 个 headless 站怎么处理？** 先人工录（推荐），还是现在就引入浏览器渲染？
