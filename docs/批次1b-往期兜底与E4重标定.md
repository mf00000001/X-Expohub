### 2.3 往届明细

17 个往届展期，月份全部落回合理区间。其中 3 个值得单独看：

| id | 往届展期 | 距今天 | 判断 |
|---|---|---|---|

## 3. 往期数据的正确用法（三条，以及一条红线）

| 用途 | 用法 | 可靠性 |
|---|---|---|
| **典型月份** `typical_month` | 推断「这个展通常在几月办」，供 B5 行程节奏、B6 撞期判断 | 高。一个有 20 届历史的展，办展月份非常稳定 |
| **站点新鲜度** `stale` | 往届距今 >24 个月 → 疑似停办/长期未更新，需人工核 | 中。也见过只更新公众号不更新官网的 |
| **同月环比基线** | 与该展去年同月的展商数/观众数对比，判断今年规模是涨是缩 | 待批次 2 有数据后启用 |

**红线：往届日期绝不能进入任何「距开展天数」的计算。**

这不是假想的风险。CIMT 的往届展期是 2025-04-21，若直接当作 `start_date`：
`(2025-04-21 − 2026-11-03).days = -561`，而 `-561 ≤ 180` 会被判成"充裕"，
用户看到"距开展 -561 天，展位充裕"。它不会报错，只会安静地流进决策。

因此字段名做了硬隔离：往届一律叫 `prev_start_date` / `prev_end_date`。
**字段名本身就是防线**——任何一个忘了看 `dates_status` 的调用方，
拿到 `prev_start_date` 也会意识到这不是本届。

## 4. E4 重标定：门限为什么必须降级

### 4.1 证据

原设计（维度清单 10.5）里 E4 是**门限**，两个因子：截止日倒计时 + 距开展天数。

| 因子 | 实测可用 | 结论 |
|---|---|---|
| 报名截止日 | **0 / 80** | 完全不可用。80 个站一次全量 + 一次重跑，两个批次都抽到 0 条；页面上一处都没写，偶有"额满即止"这类非日期表述 |
| 距开展天数 | 35 / 80 (44%) | 唯一还站得住的锚 |
| 售罄速度 / 余量 | 0 / 80 | 依赖展商名录，批次 3 才有 |

把这两个因子代入真实数据跑一遍，得到：

```
E4 档位分布（80 个可用展会）
  unknown   45   (56%)   ← 无任何日期
  ample     17   (21%)
  normal    11   (14%)
  urgent     4   (5%)
  critical   3   (4%)
  ─────────────────────
  gate 触发   0   (0%)   ← 关键
```

**0 次。** 在这批数据上，E4 当门限等于不存在。

### 4.2 为什么不能硬撑成门限

如果把「距开展 ≤180 天」都当门限，44% 的覆盖率会制造大量假否决。
假否决的代价是**不可逆的**——用户永久失去一个本来能去的展会；
而漏判（该拦没拦）只是让用户多花点时间自己判断，可以恢复。

在这种不对称下，门限的判定条件必须保守到接近苛刻。

### 4.3 新的分层

E4 拆成两件不同的事：

| 层 | 触发条件 | 性质 | 作用 |
|---|---|---|---|
| **窄门限** | 本届已结束，或距开展 ≤ **3 天** | 布尔，一票否决 | 「来不及了」——这是唯一有确凿证据的否决 |
| **紧迫度提示** | 距开展 4 天 ~ 无限远 | 五档分级，只提示 | 「该什么时候联系主办方」 |

新档位（`START_WINDOW_BANDS`）：

| 距开展 | 档位 | 提示语 |
|---|---|---|
| >180 天 | `ample` | 早鸟期，位置最全 |
| 90~180 天 | `normal` | 正常招展期 |
| 45~90 天 | `tight` | 偏紧 |
| 15~45 天 | `urgent` | 紧，该现在就联系主办方 |
| 4~14 天 | `critical` | 很紧，基本只剩边缘位 |
| 0~3 天 | `impossible` | 基本不可能，除非主办方现场售位 |
| 已结束 | `closed` | 本届已无法再订展位 |

档位名刻意避开了 `closed` 被滥用：距开展 5 天在旧实现里会得到 `closed`，
字面意思是"通道关闭"，但实际只是"没好位置"——这两个结论对用户的行为指引完全不同。

### 4.4 E4 什么时候能恢复门限

**批次 3 拿到展商名录之后。** 名录能算出一个真正的余量指标：

```
余量率 = (展位总数 − 已报名展商数) ÷ 展位总数
```

有了它，E4 才能说「确实没位了」，而不只是「来不及了」。在那之前，
E4 保持提示身份，不进否决链。

## 5. 权重怎么调（本次决定）

原设计已否掉加权和（维度清单 10.1：加权允许"一项极差被其他项抵掉"）。
E4 降级后，权重问题变成另一个问题：**v1 里到底还剩几个因子真的在起作用？**

| 画像 | v1 可用性 | 角色 |
|---|---|---|
| E1 客群可得性 | 观众/展商比可算（批次 2 补数据） | **主因子** |
| E2 竞争密度 | 需展商名录（批次 3） | 暂缺，`k` 置 1.0（不惩罚） |
| E3 成本效率 | 需用户填 4 个数 | 用户侧计算器 |
| E4 展位可得性 | 44% 覆盖，0 次门限 | **降为紧迫度提示** |
| E5 交付可行性 | 布尔清单，零数据依赖 | **唯一硬门限** |
| E6 历史兑现 | 空表 | 不参与 |

**结论：v1 不设权重，改用字典序（lexicographic）判定。**

```
1. E5 硬约束不满足          → 停（或输出额外成本）
2. E4 窄门限触发（≤3 天/已结束）→ 停
3. E1 观众/展商比 <8        → 大幅降级（摊薄严重）
4. E2 折扣 k（有名录才算）   → 乘到 E1 上
5. E3 N* 对比               → 用户侧最终确认
```

为什么用字典序而不是权重：**加权和会把"消防不过"和"价格便宜"放在同一个天平上**，
而实际上前者是约束、后者是偏好。字典序保证了约束永远先于偏好生效，
不需要标定任何系数——这也是在只有 80 个样本、0 条标注的情况下唯一站得住的做法。

**呈现方式仍按维度清单第 11 节的倾向：三档结论（推荐 / 可考虑 / 不建议）+ 理由清单，
不给总分。** 总分会让用户以为 78 分和 82 分的差别有意义，而实际上两者的数据来源
可能一个是 `jsonld`（可靠）、一个是正则误抽（不可靠）。

### 6.3 防幻觉闸门（这是整个 LLM 方案唯一的防线）

模型抽字段最大的风险不是抽错，是**抽出一个格式完美、日期合理、页面上根本不存在的值**。
这类错误在下游看起来毫无破绽，比空值危险得多。

因此每个字段必须带 `evidence`（正文里逐字出现的原文），然后机器核验：

| 检查 | 规则 |
|---|---|
| 依据真实存在 | 去掉空白后 `evidence` 必须是正文的子串，否则整条丢弃 |
| 依据撑得住取值 | 日期类：拿 `evidence` 跑 `extract_dates`，取值必须等于抽出的起止日之一 |
| | 文本类：取值本身必须出现在 `evidence` 里 |
| 依据不能太短 | <4 字直接判无效（"举办"这种证明不了任何事） |
| 归属正确 | `start_date` 必须是未来、`prev_start_date` 必须是过去，不符则丢弃 |

被丢弃的字段不会静默消失，全部记在 `dropped` 里并注明原因——
这样「模型抽了但被拦下」和「模型没抽到」可以区分，前者才是 prompt 需要改进的信号。

用这五条挡住之后，LLM 的部分只能带来"有据可查"的字段。这会把上限压得比裸跑 LLM 低，
但换来的是：**每一个进入数据集的字段都能点回原文。**

## 8. 这一轮暴露的方法论问题

**「先设计再验证」在本项目上会反复翻车。** E4 的截止日倒计时写在文档里毫无问题，
一上真实数据就是 0% 覆盖；organizer 的抽取规则改了四版（黑名单 → 包含判定 →
结尾判定 → 去主语）才从"抽成营销句"变成 87% 准。这两件事都不是设计能预见的。

唯一有效的做法是：**每个字段都先小样本跑一遍，拿到填充率和抽样正确率，再决定它在决策链
里的位置**。这也解释了为什么本次要改 E4 的角色而不是硬撑——角色应该跟着数据走，
不是数据跟着设计走。
